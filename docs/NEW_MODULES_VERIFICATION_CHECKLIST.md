# Verification Checklist — Estimation & Reservation Modules

This document is for whoever runs the **first real build** of the Estimation
(customer quotations) and Reservation (table-booking scheduler) modules added
across four commits on `claude/project-estimation-man-hours-feon9i`. Every
line of C#/XAML/TypeScript in those commits was hand-written and reviewed for
structural consistency (brace balance, XML well-formedness, method-signature
cross-referencing against existing code) — but **none of it has been
compiled or run**, because this environment has no .NET SDK. Treat this as
an unverified diff, not a tested feature.

## 1. Prerequisites

- .NET 10 SDK
- Microsoft SQL Server (LocalDB is fine) reachable via the connection string
  in `src/API/appsettings.Development.json` / `src/HotelPOS/appsettings.json`
- Node.js + Angular CLI (only if verifying `HotelPOS.Client`)

## 2. Build order (cheapest failure signal first)

1. `dotnet restore HotelPOS.sln`
2. `dotnet build HotelPOS.sln --configuration Release` — this alone should
   catch the majority of possible mistakes: namespace/using errors, wrong
   method signatures, XAML compile errors (`x:Name` field generation,
   `InitializeComponent`, `StaticResource` lookups that don't resolve).
3. `dotnet ef database update --project src/Infrastructure --startup-project src/API`
   (or the WPF startup project) — applies the two hand-authored migrations.
4. `cd src/HotelPOS.Client && npm ci && npm run build` (or `ng build`) —
   catches TypeScript/template errors in the Angular pieces.
5. `dotnet test HotelPOS.sln --configuration Release` — runs the full suite
   including the new tests listed in §5.

## 3. Highest-risk areas, in order of how likely I'd bet they break something

1. **The hand-authored EF Core migrations.** `20260804070000_AddEstimationModule`
   and `20260804090000_AddReservationModule` (plus their `.Designer.cs` and the
   edited `HotelDbContextModelSnapshot.cs`) were built by manually inserting
   entity/relationship blocks into the snapshot and mirroring that into a
   Designer.cs, then hand-writing `Up()`/`Down()` — normally all
   auto-generated by `dotnet ef migrations add`. If `dotnet build` or
   `dotnet ef database update` reports a mismatch between the snapshot and
   the actual model, **don't hand-patch further** — delete both migration
   pairs and the two new entity blocks won't need to change; just run:
   ```
   dotnet ef migrations add AddEstimationModule --project src/Infrastructure --startup-project src/API
   dotnet ef migrations add AddReservationModule --project src/Infrastructure --startup-project src/API
   ```
   The `Estimation`/`EstimationItem`/`Reservation` entity classes and the
   `HotelDbContext` Fluent config are the actual source of truth; the
   migration files are just a derived artifact I approximated by hand.
2. **WPF XAML resource references.** Both new views (`EstimationView.xaml`,
   `ReservationView.xaml`) reuse `StaticResource` keys copied from
   `PurchaseEntryView.xaml` (`PremiumCard`, `PremiumGrid`, `CenterHeader`,
   `RightHeader`, `CenterCell`, `HeroTextBlockStyle`, `BodySmallTextBlockStyle`,
   `H3TextBlockStyle`, `PrimaryBtn`, `SecondaryBtn`, `HeaderBrush`,
   `AppBackground`, `SuccessBrush`, `PrimaryBrush`, `DangerBrush`,
   `TextPrimary`, `TextMuted`, `NavBtn`) — these should already exist
   globally, but only WPF's XAML compiler will confirm every reference
   resolves.
3. **CommunityToolkit.Mvvm source-generated names.** `[RelayCommand]`/
   `[ObservableProperty]` generate command/property names I referenced in
   XAML bindings (e.g. `SaveEstimationCommand`, `MarkAsSentCommand`,
   `RefreshReservationsCommand`, `MarkCheckedInCommand`). A typo in either
   the C# method name or the XAML binding string won't be caught by anything
   except the XAML compiler/runtime binding.
4. **`partial void OnSelectedDateChanged(DateTime value)`** in
   `ReservationViewModel.cs` — relies on CommunityToolkit.Mvvm's optional
   generated property-changed hook firing correctly on `SelectedDate`.
5. **`TimeSpan` JSON round-trip** for `Reservation.StartTime`/`EndTime` —
   modeled on the existing `Attendance.CheckInTime`/`CheckOutTime` pattern
   (proven to work), but verify a real `POST /api/reservations` with
   `"StartTime": "19:00:00"` actually binds correctly.

## 4. Module-specific things worth a deliberate look

### Estimation
- `ConvertEstimationToOrderCommandHandler` calls `IOrderService.SaveOrderAsync`,
  which requires an **open cash session** — confirm the WPF/Angular
  "Convert to Order" action surfaces that error cleanly if no shift is open,
  rather than a confusing failure.
- FluentValidation is wired in the API (`Program.cs`) but **not** the WPF
  app's DI (same as every other module, e.g. Purchases) — so WPF-side
  validation is only the manual checks in `EstimationViewModel`. Worth a
  manual test of the WPF form's edge cases (empty number, zero-quantity row).

### Reservation
- Overlap-conflict detection (`ReservationOverlapChecker`) is unit-tested
  against a mocked repository — worth one real end-to-end test: book two
  overlapping slots on the same table via the API/UI and confirm the second
  is rejected with a clear message, and that back-to-back (non-overlapping)
  slots are allowed.
- `PATCH /api/reservations/{id}/status` is a new endpoint shape (others in
  this codebase use full-object `PUT`) — confirm `HttpClient.PatchAsync`
  content-type negotiation works as expected against the real API (the
  Angular/WPF/test code all assume a JSON body `{ "status": "..." }`).

## 6. Manual smoke test (once the build is green)

1. Log in as Admin. Confirm **Estimations** and **Reservations** appear in
   the sidebar nav (WPF and Angular) without needing any manual permission
   setup — both new permission modules are seeded for Admin/Manager and
   auto-picked-up by role creation (`PermissionModules.All`).
2. **Estimation**: create a Draft estimation with 1–2 items → mark Sent →
   mark Accepted → Convert to Order (with a cash session open) → confirm a
   real order appears in Orders/Billing with the same items.
3. **Reservation**: book Table A for 19:00–20:00 → attempt to book Table A
   again for 19:30–20:30 on the same date (expect a clear rejection) → book
   Table A for 20:00–21:00 (should succeed, no overlap) → Check In → Complete.
4. Confirm a Cashier-role token gets `403 Forbidden` on both modules' write
   endpoints (seeded permissions only grant Admin/Manager, same convention
   as Purchases/Tds/etc.).

## 7. If something's broken

Given the scale of this diff (3 new modules across 5 layers, ~40+ new
files, two hand-authored migrations), finding *some* build errors on first
compile would be unsurprising — that's expected, not a sign the approach was
wrong. Fix forward against the compiler's actual errors rather than
re-guessing; the domain/business logic (overlap detection, status
transitions, capacity checks) is the part most worth preserving carefully,
since it's already unit-tested and reasoned through — the mechanical
glue (DI registrations, XAML resource names, migration boilerplate) is
where a typo is most likely and least consequential to fix.
